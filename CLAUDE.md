# CLAUDE.md — working agreement for the SAVANT project

This file tells any AI collaborator (Claude, Cursor, etc.) how to work in this repository. Read it before editing code.

---

## 1. Research goals (north star)

SAVANT is a research artefact, not a product. Every change should serve at least one of:

1. **Synthesis** — produce a faithful, machine-readable description of the soccer action valuation literature.
2. **Gap discovery** — make underexplored regions of the design space visible and falsifiable.
3. **Benchmarking** — give honest, reproducible, calibrated comparisons of xT, VAEP, Atomic-VAEP, and EPV-style baselines on StatsBomb Open / 360.
4. **Manuscript** — every claim in the paper must be backed by an artefact in `data/outputs/` or a result generated by `scripts/`.

If a proposed change does not serve one of these, push back before implementing it.

---

## 2. Coding rules

- **Language / version.** Python 3.11. No code that requires a newer interpreter.
- **Package layout.** All importable code lives under `src/savant/`. Scripts in `scripts/` are thin CLI wrappers — they parse args, load config, and call into the package.
- **Config over constants.** Paths, model ids, temperatures, seeds, and dataset splits live in `configs/*.yaml`. Do not hardcode them in modules.
- **Schema first.** Anything written under `data/outputs/extractions/` must validate against `configs/extraction_schema.json`. When the schema changes, bump the `schema_version` field and write a migration note in the PR.
- **Determinism.** Every script that trains or evaluates a model must accept `--seed` and log it alongside results.
- **Logging.** Use `savant.utils.logging` (to be added). No bare `print` in library code.
- **Style.** `ruff` for lint/format, `mypy --strict` for the package. Tests in `pytest`. Keep functions small and typed.
- **No silent network calls.** LLM / StatsBomb fetches go through a single client module that logs every request and respects an offline-mode flag.
- **No commits of data.** `data/` content is gitignored except for `.gitkeep` markers and tiny fixtures used by tests.

---

## 3. Agent design rules

- One Markdown prompt per agent, in `prompts/`. Prompts are the source of truth — code loads them, does not duplicate them.
- Every agent call returns **structured JSON** validated against a schema. Free-form prose is wrapped inside a string field, never the whole response.
- Every agent has a **critic** pass option: a second cheaper model that checks the structured output against the source text and either accepts, requests revision, or rejects. The critic's verdict is logged.
- Agents are deterministic-by-default: temperature ≤ 0.2, with seed when supported.
- Token budgets, model ids, and retry policy live in `configs/agents.yaml`, not in code.

---

## 4. Benchmark integrity rules

- **Data hygiene.** Split by *match*, never by event. No event from a match in the test set may appear in training.
- **Leakage audit.** Each benchmark task ships with an automated leakage check; the run aborts if it fails.
- **Metrics.** Report calibration (Brier, ECE) and discrimination (ROC-AUC, log-loss) in addition to whatever each method's paper used. Report bootstrap CIs.
- **Compute disclosure.** Every benchmark result row carries `train_seconds`, `inference_seconds`, `peak_ram_mb`, `hardware`.
- **No silent re-ranking.** If the leaderboard changes between runs, the diff must be committed alongside the result.

## 5. Step-by-step implementation workflow

Implement in this order. Do not skip ahead — later stages depend on the contracts established by earlier ones.

### Stage 0 — Scaffolding (current)
- Folder structure, `README.md`, `CLAUDE.md`, `extraction_schema.json`, placeholder prompts.
- **Exit criterion:** user reviews scaffold and approves.

### Stage 1 — Config + utils
- `configs/paths.yaml`, `configs/agents.yaml`, `configs/benchmark_tasks.yaml`.
- `savant.utils`: config loader, logging, IO helpers, deterministic seeding.
- Tests for config loading and schema validation.

### Stage 2 — Ingestion
- PDF parsing (PyMuPDF / GROBID) → per-paper text + metadata in `data/raw/`.
- Chunking + section detection → `data/processed/`.
- Deduplication on title / DOI.

### Stage 3 — Extraction
- LLM client wrapper (offline mode, prompt logging, JSON-mode call).
- `extraction_agent` runner with critic loop.
- Per-paper records in `data/outputs/extractions/{paper_id}.json`.

### Stage 4 — Taxonomy + Knowledge Graph
- Taxonomy agent normalises free-text fields against controlled vocabularies (which the agent helps construct, with a human-reviewed seed list).
- KG built in NetworkX initially; export to RDF / Neo4j later if needed.

### Stage 5 — Gap analysis
- Coverage matrices over (method family × data source × evaluation metric × task).
- Gap-scoring heuristic + agent-written rationale per top-K gap.

### Stage 6 — Benchmarking
- StatsBomb loader (Open Data first, 360 behind a flag).
- Reference implementations: xT (grid), VAEP, Atomic-VAEP, EPV-style.
- Shared evaluation harness; leaderboard CSV + figures.

### Stage 7 — Manuscript
- LaTeX skeleton with section stubs and `\input{}` includes already wired.
- Manuscript agent fills sections from extraction DB + benchmark artefacts.
- Every numerical claim cites the artefact path that produced it.

### Stage 8 — Polish
- Notebooks as demos, not as pipeline drivers.
- End-to-end `make all` (or `invoke all`) that rebuilds the paper from raw PDFs + StatsBomb data.

---

## 6. What to ask the user before doing

- Changing the extraction schema (breaks downstream artefacts).
- Adding a new agent or removing an existing one.
- Bringing in a non-open dataset.
- Anything that costs > a few dollars of LLM spend in a single run.
- Pushing to a remote, creating a PR, or running `ultrareview`.

---

## 7. What to do without asking

- Fix bugs in your own newly written code.
- Add tests.
- Refactor inside a single module if behaviour is unchanged.
- Update `README.md` or `CLAUDE.md` when the conventions actually change (not speculatively).
